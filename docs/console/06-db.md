# `call db` — database connectivity and migrations

Operations across all `DbConfig` connections registered in the project
(and optionally in plugins). Three subcommands:

- `ping` — check connection + measure latency
- `migrate` — apply schema/table/index/constraint DDL to the database
- `sql` — print the SQL `migrate` would execute, without running it

---

## Synopsis

```
call db <command> [-flags] [--plugin=<name> | --plugins]
```

| Command   | Purpose                                                    |
|-----------|------------------------------------------------------------|
| `ping`    | Connect to every configured DB, report driver/DSN/latency  |
| `migrate` | Run DDL against connected databases                        |
| `sql`     | Render DDL to stdout (no execution)                        |
| `pool`    | Show connection-pool utilisation of the running server     |

`migrate` and `sql` are filtered by **kind flags** and **plugin scope**.

---

## Kind flags (apply to `migrate` and `sql`)

| Flag | Selects                                                       |
|------|---------------------------------------------------------------|
| `-e` | Extensions (pgsql only — `CREATE EXTENSION`)                  |
| `-s` | Schemes (pgsql only — `CREATE SCHEMA`)                        |
| `-t` | Tables (`CREATE TABLE`)                                       |
| `-i` | Indexes (`CREATE INDEX`)                                      |
| `-c` | Constraints (`ALTER TABLE ... ADD CONSTRAINT`)                |

If no kind flags are passed, **all of them** run (`-e -s -t -i -c`).
For mysql, `-e` and `-s` are silently skipped at execution time.

### Idempotency

`migrate` swallows the driver-specific "already exists" codes and prints
`[EXIST]` instead of `[FAILED]`:

| Driver | Code     | Meaning                            |
|--------|----------|------------------------------------|
| pgsql  | `42P06`  | Schema already exists              |
| pgsql  | `42P07`  | Table / index already exists       |
| pgsql  | `42710`  | Constraint already exists          |
| mysql  | `42S01`  | Table already exists               |
| mysql  | `42000`  | Index already exists (syntax-ish)  |

So `call db migrate` is safe to re-run.

---

## Plugin scope (apply to all subcommands)

| Option              | Targets                                                    |
|---------------------|------------------------------------------------------------|
| _(none)_            | The app (`Project` label)                                  |
| `--plugin=<name>`   | One registered plugin                                      |
| `--plugins`         | Every registered plugin                                    |

`ping` always also pings the app's own configs in addition to the
explicit selection.

---

## `call db ping`

Walks every `DbConfig` (`PPAMapping::scanningConfigs()`) for the
selected target, calls `$config->setUp()` then `$config->pingDetail()`,
and prints driver, DSN, latency, and status.

```bash
call db ping
call db ping --plugins
call db ping --plugin=bill
```

Sample output:

```
 | [============ Db ============]
 | [ [Project] App\Configs\Database\Main ]
 |   driver       pgsql
 |   dsn          pgsql:host=db;port=5432;dbname=app
 |   latency      1.42 ms
 |   App\Configs\Database\Main ......... [OK]
```

---

## `call db migrate`

For each `DbConfig` marked `#[Migratable]` (sorted by priority
High → Normal → Low), reads every `#[Table]` entity, builds DDL, and
executes it grouped by kind. Only opted-in configs run.

```bash
call db migrate                      # app, everything
call db migrate -t -i                # app, tables + indexes only
call db migrate --plugin=bill        # one plugin only
call db migrate --plugins            # every plugin
call db migrate --plugins -t         # every plugin, tables only
```

A config with no `#[Migratable]` is skipped with a warning. A target
with no `#[Table]` entities is also skipped.

`DEBUG=true` in the environment surfaces the underlying SQL error on
`[FAILED]` rows.

## `call db pool`

Shows how loaded the connection pools are, aggregated over the workers of a **running**
server:

```bash
call db pool
```

```
App\Config\AppDb
  active 12 · idle 3 · total 15 · maximum 20 · workers 2
  saturated  1 of 2 workers                    [SATURATED]
per worker
  worker#0  App\Config\AppDb  active=2  idle=3 total=5  max=10  age=0s
  worker#1  App\Config\AppDb  active=10 idle=0 total=10 max=10  age=3s
```

A pool lives inside the server's memory and the CLI is a separate process, so this reads
what each worker publishes to the shared store — not the pool itself. Two consequences:

- numbers are as fresh as the last publish (the `age` column), controlled by
  `PPA_POOL_TELEMETRY` (seconds, default `5`, `0` disables);
- with no server running, the command says so instead of printing an empty table.

**Saturation is counted per worker**, never derived from the totals: a borrow queues on
its own worker's pool, so one blocked worker matters even while the fleet looks roomy.

See [`../ppa/17-pool.md`](../ppa/17-pool.md).

## `call db sql`

Same scanning + DDL generation as `migrate`, but writes statements to
stdout instead of executing them. Useful for code review, CI diffs, or
piping to a file:

```bash
call db sql --plugin=bill -s         # just the CREATE SCHEMA lines
call db sql -t > schema.sql          # capture all tables
call db sql                          # everything, all kinds
```

Output is grouped per config and per kind, in execution order.

---

## Examples

```bash
call db ping
call db ping --plugins
call db migrate
call db migrate -t -i
call db migrate --plugin=bill
call db sql --plugins -t
call db sql --plugin=bill -s
```
