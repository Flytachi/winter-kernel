# Docker

Notes for running Winter inside a Docker image. The full image template is generated by `call cfg docker --fpm` (or `--swoole`); this page focuses on the **operational pitfalls** that bite real deployments — most importantly file ownership inside the storage tree.

---

## Storage permissions: the build-time root trap

Every command that runs in a `RUN` step of a Dockerfile executes as **root** (unless you switch via `USER ...`). Whatever directories root creates during build end up owned by `root:root`, and a downstream non-root runtime user (`winter`, `www-data`, `app`, …) cannot write to them.

In Winter the most common offenders are the cache directories used by:

- the route map (`storage/volatile/mapping.php`)
- the DI scanner (`storage/volatile/di.php`)
- thread / job payloads (`storage/runnable/*`)
- any `Kernel::store('foo')` call

### What the framework guarantees

The kernel itself is **lazy** about creation:

- `Kernel::init()` only **computes** `Kernel::$pathStorageVolatile`. It no longer creates the directory.
- The first call site that actually writes (`KernelStore::volatile()`, `Router::dumpCache()`, `Scanner::writeCache()`) creates the directory through `KernelStore::ensureDirectory()`, which uses `umask(0)` so the resulting mode is exactly `0777`, not `0755` after umask trimming.

So a benign maintenance command like `call cfg completion -if` no longer touches `/storage/volatile/` at all, and any directory that is created at build time gets a permissive mode.

### What you still need to do in the Dockerfile

The framework handles modes; **ownership** is your job. Two patterns work cleanly:

#### Pattern A — defer creation to runtime (recommended)

Don't run any framework command that writes to `/storage` during the image build. Let the runtime user create the directories on the first request. Mode `0777` is enough for any process to write later.

```dockerfile
# Setup application user (no shell, no home — pure runtime identity)
RUN adduser -D -H -s /sbin/nologin winter \
    && adduser winter nginx

# Copy code, then hand the writable tree to the runtime user
COPY --chown=winter:nginx . /var/www/html
RUN chmod -R 775 /var/www/html/storage /var/www/html/public

# Install zsh completion as a per-user shell artefact —
# but run it AS A USER, not as root.
USER winter
RUN /var/www/html/dev/call cfg completion -if || true
USER root
```

Two things matter here:

1. `COPY --chown=winter:nginx` puts the source tree under the right ownership in one step.
2. `USER winter` flips the active user **before** any framework command runs. After the command, switch back with `USER root` so subsequent `RUN`s (e.g. nginx config) work.

If you do not need shell completion in production images at all, **just delete the line** — that solves the permission trap entirely.

#### Pattern B — chown after maintenance commands

If you must run framework commands as root (legacy build chain, complex `entrypoint.sh` setup), re-chown the storage tree at the end:

```dockerfile
COPY . /var/www/html
RUN adduser -D -H -s /sbin/nologin winter \
    && adduser winter nginx

# Maintenance commands here may run as root — just re-chown afterwards.
RUN /var/www/html/dev/call cfg completion -if

RUN chown -R winter:nginx /var/www/html \
    && chmod -R 775 /var/www/html/public \
    && chmod -R 775 /var/www/html/storage
```

The `chown -R … /var/www/html` at the end **re-flattens** ownership of everything the previous root commands may have created.

### Anti-pattern — chown then run as root

This was the original bug pattern that caused `Job::dispatch()` to fail with `EACCES`:

```dockerfile
# ✗ Wrong order:
RUN chown -R winter:nginx /var/www/html \
    && chmod -R 775 /var/www/html/storage

RUN ./call cfg completion -if   # root runs this, creates root-owned dirs
                                # below the already-chowned tree
```

The `chown` happens first, the framework command runs second, and the new directories sneak in **after** the chown — owned by `root`. Switch the order, or use Pattern A above.

## Volatile directory location — `isTmpVolatile`

`Kernel::init()` accepts an `isTmpVolatile` flag that decides where `pathStorageVolatile` lives:

| `isTmpVolatile` | Resolves to | When to use |
|---|---|---|
| `false` *(default in `K2\Kernel`)* | `<pathStorage>/volatile` | Long-lived deployments where you want the route cache and DI cache to persist with the rest of `storage/`. |
| `true` | `sys_get_temp_dir() . '/flytachi.winter.volatile.<basename(pathRoot)>'` | Immutable container images. Cache is rebuilt from scratch on each container start, no persistence needed. Avoids leaving stale state in a layer. |

For Docker, `true` is often the cleaner choice:

```php
// bootstrap.php
class Boot extends BaseBoot
{
    protected static function configure(): void
    {
        Kernel::init(
            pathRoot:      __DIR__,
            isTmpVolatile: true,    // route + DI cache live in /tmp
        );
    }
}
```

The temp directory is auto-created on first use (via `KernelStore::ensureDirectory`) with mode `0777`, owned by whichever user runs PHP-FPM. Inside a container `/tmp` is local to the container's writable layer, so cleanup happens automatically when the container is removed.

## DEBUG flag in production images

Set `DEBUG=false` in the production image's `.env` (or as a container environment variable). This:

- enables the route-cache write on first boot (`Router::resolve()` writes `storage/volatile/mapping.php`)
- enables the DI cache write on first boot (`Scanner` writes `storage/volatile/di.php`)
- silences PHP error reporting
- switches `ExceptionResponseBase` to short JSON / minimal HTML responses

To force a cache rebuild after a deployment without restarting the container, run the matching console command — `call mapping clean && call di clean` and let the next request rebuild.

## Logging

In containerised deployments prefer:

```dotenv
LOG_OUTPUT=auto      # detected as 'syslog' inside Docker
LOG_FORMAT=json      # ready for Loki / Datadog / ECS log shippers
```

`auto` detection looks at `KUBERNETES_SERVICE_HOST` and `/.dockerenv` — both present in containerised environments — and routes everything to `syslog`. Combined with the syslogd `runit` service in the official image template, every PHP write reaches stdout in JSON form.

See [`../configuration/02-logging.md`](../configuration/02-logging.md) for the full env reference.
